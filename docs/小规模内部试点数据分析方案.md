# 小规模内部试点数据方案

## 摘要

这次试点预计只有几位到十几位参与者、持续数天。我们主要想知道：**有没有人愿意开始用、聊下去时体验如何、哪些环节让人停下，以及下一版应该改什么。**数据用来发现产品问题和积累真实案例，不用来证明心理健康改善或推算企业整体使用率。

试点前由邀请人记下实际邀请了多少人、邀请日期和测试起止日期。系统只能识别不同浏览器，不能知道邀请链接实际被谁打开；同一个人用手机和电脑也可能被算作两个使用身份。结束后先报原始人数，再解释行为与反馈，不只给百分比。

## 这次看什么

| 指标 | 这次怎么统计 | 数据从哪里来 | 能回答什么 |
| --- | --- | --- | --- |
| 实际邀请人数 | 邀请链接实际发给了多少位不同的人 | 邀请人手工记录 | 试点触达范围；系统不能自动得出这个数 |
| 进入身份数 | 观察到多少个新的浏览器身份进入 | 进入记录 | 入口是否有人使用；可能高于实际人数，不能直接算精确的邀请转化率 |
| 首次聊天人数 | 进入后，至少发出一条消息的浏览器身份数 | 聊天行为记录 | 有多少人真正开始体验核心功能 |
| 聊到三轮的人数 | 至少发出三条消息的浏览器身份数 | 聊天行为记录 | 有多少人愿意继续聊；三轮只是观察门槛，不等于聊天有价值 |
| 回复是否正常 | 用户消息与成功生成的 AI 回复各有多少；另记实际遇到的超时、错误 | 聊天记录、故障记录 | 核心流程是否稳定；仅靠行为记录不能确认用户最终看到了回复 |
| 聊天评价 | “有帮助／一般／没有帮助”各多少次；评价提示出现但没回答的有多少次 | 聊天中的轻反馈 | 用户的即时感受及作答情况；未回答不能算负面评价 |
| 活动使用 | 打开、开始、完成活动的浏览器身份数；完成后如何评价 | 活动使用与评价记录 | 哪一步有人停下、哪些内容值得改；不能把完成直接当成有效果 |
| 再次使用 | 同一浏览器身份是否在另一天回来聊天或参加活动 | 不同日期的使用记录 | 短期回访；试点只有几天时不计算七日留存 |
| 主动意见与具体问题 | 参与者写下的反馈、负面评价对应的聊天片段，以及重复出现的问题 | 反馈建议、限定研究人员的对话审阅、简短访谈 | 为什么满意或不满意，下一版优先改什么 |

## 结束后怎么用这些数据

先按表格顺序写出一条简洁的过程：**邀请了多少人 → 观察到多少个身份进入 → 多少个开始聊天 → 多少个聊到三轮 → 收到多少次评价。**每一步同时列出原始数量和已知的中断原因。再挑选正面、一般、负面及中途停止的聊天，记录具体问题：用户想解决什么，产品如何回应，哪里做得好或不好。

最终只需形成两类结论：一是这次试点实际发生了什么；二是下一版要改的两三个问题，以及支持这些判断的行为、评价或对话例子。样本少时，一位用户的多次点击不能算作多位用户；没有回答的人不能被推断为满意或不满意。对外展示时称为“早期试点观察”，将真实数据与演示数据分开。
