# 内测组织与研究数据字典

当前组织与入口以[组织、入口与地址](组织-入口-地址.md)为准。钉钉企业入口与网页邀请入口使用同一套 CARE 业务表和匿名会话；身份映射仍在独立的 IDENTITY_DB。本文件记录研究字段与分析口径，后半部分的实施顺序是当时的设计记录，不能当作当前部署状态。评审演示数据只归属于评审组织，不存在跨组织共享的模拟基线。

## 目标与边界

内测者无需提供姓名、手机号或微信身份。同一浏览器内可延续匿名身份；清除浏览器数据或更换设备后允许产生新身份，不承诺跨设备找回。内部研究人员需要按一个匿名主体串联其聊天、广场、活动和反馈，进而改进产品。企业联系人只能接收达到最小样本阈值的组织汇总，不能访问逐人轨迹、个案编号或原文。

这里的“匿名”指对其他参与者和企业联系人不显示真实身份；`anonymous_user_id` 是可关联的假名标识，不应称为不可识别的匿名数据。小组织中的时间、内容和行为组合仍可能使人被推断出来。测试说明须准确告知参与者我们会分析逐人的假名使用记录及内容如何处理。

## 身份与组织

| 字段 | 含义与规则 |
| --- | --- |
| `organization_id` | 随机内部 ID；一家公司或一个明确的测试批次对应一个 ID。不得由客户端自行指定。 |
| `organization_name` | 内部管理用名称；不放入研究事件或员工端响应。 |
| `entry_channel` | `beta_web` 或 `dingtalk`。入口分别认证，进入业务层后使用统一会话上下文。 |
| `anonymous_user_id` | 随机稳定 ID；在一个组织内代表一个浏览器身份。另一个组织重新生成 ID，不跨组织关联。沿用业务层现有的 `anon_id` 概念，避免两套主体主键。 |
| `session_digest` | 服务端保存的会话凭证摘要；原始凭证只在 HttpOnly、Secure Cookie 中。会话过期可通过仍有效的浏览器身份凭证续签；后者也只能保存摘要，须支持撤销。 |
| `invite_digest` | 邀请码摘要；原码只在生成时显示。邀请码可设有效期、加入上限与停用状态。它证明持有链接，不证明在职身份。 |

统一业务库采用 `organizations`、`subject_organizations`、`beta_invites`、`beta_memberships`，并让 `sessions` 能解析出 `organization_id`、`anonymous_user_id` 与 `entry_channel`。`organization_capabilities` 单独控制外部数据权限；公开组织不会因为属于某个组织就获得钉钉考勤能力。原有 `tenant_profile` 是路演模拟档案，不能充当真实组织表。

钉钉入口保留原认证与身份映射，网页内测入口单独实现；不要把当前 `/api/auth/demo` 用作内测登录。它每次生成新 ID，也没有组织边界。业务接口应只接受服务端解析出的会话上下文，不能相信请求体里的组织或用户 ID。

## 业务数据归属

| 数据 | 主体关联 | 组织边界与读取规则 |
| --- | --- | --- |
| `profiles` | `anonymous_user_id` | 一人一组织；内部显示名仅用于用户界面。 |
| `conversations`、`messages`、`conversation_state`、`model_runs` | `anonymous_user_id`、`conversation_id` | 本人只能读自己的对话；研究导出可按组织和主体筛选。原文继续密文保存。 |
| `posts` | `organization_id`、`anonymous_user_id` | 广场列表必须按组织过滤。 |
| `post_replies`、`post_reactions` | `post_id`、`anonymous_user_id` | 写入前验证帖子属于当前组织；读取随帖子范围过滤。 |
| `resource_events`、活动参与和反馈 | `anonymous_user_id`、`activity_id` | 可关联推荐、打开、开始、完成、反馈；组织从会话或成员关系取得。 |
| `appointments`、授权与个案 | `anonymous_user_id`、个案 ID | 保持现有本人授权与疗愈师权限；至少保留来源组织以便筛选。 |
| `aggregate_events` | 当前不含主体 ID | 继续服务组织汇总，不能当作逐人研究事件表。 |

广场列表、回复和反应接口均按会话组织过滤，企业管理统计也只读取企业组织。统一业务数据库从空数据开始，不导入旧钉钉数据或演示种子数据，不做历史数据回填。跨组织对象访问的回归测试已加入。

## 产品研究事件 `product_events`

已在迁移中建好追加写入的事件表，聊天、广场和活动的主要动作由服务端写入。字段如下：

| 字段 | 类型 | 规则 |
| --- | --- | --- |
| `event_id` | TEXT | 随机主键；允许幂等写入。 |
| `organization_id` | TEXT | 从会话取得，必填。 |
| `anonymous_user_id` | TEXT | 从会话取得，必填；不由浏览器上报。 |
| `entry_channel` | TEXT | `beta_web` / `dingtalk`。 |
| `event_name` | TEXT | 下表限定的事件名，不能接收任意前端字符串。 |
| `occurred_at` | INTEGER | 服务端毫秒时间戳。 |
| `object_type`、`object_id` | TEXT / TEXT | 可选关联对象，如对话、帖子、活动；只存内部 ID。 |
| `properties_json` | TEXT | 白名单结构化属性，禁止原文、自由文本、邀请码、Cookie、IP、User-Agent 和身份凭证。 |
| `schema_version` | INTEGER | 事件语义版本；初版为 1。 |

首轮事件集应少而稳定：

| 事件 | 触发时点 | 允许的属性 |
| --- | --- | --- |
| `beta_joined` | 首次取得内测身份 | 邀请批次的内部 ID；不存原邀请码。 |
| `session_started` | 成功进入应用 | `new_or_returning`。不要把每次页面刷新误计为新人。 |
| `chat_message_sent` | 消息写库成功 | `conversation_id`、轮次；风险级别可通过现有事件关联，不复制原文。 |
| `chat_reply_delivered` | 回复成功返回 | `conversation_id`、耗时区间、结果状态。 |
| `wall_post_created`、`wall_reply_created`、`wall_reaction_added` | 对应写库成功 | 对象 ID；不存帖子或回复原文。 |
| `activity_opened`、`activity_started`、`activity_completed` | 对应动作成功 | `activity_id`、内容版本、完成状态。 |
| `activity_feedback_submitted` | 反馈写库成功 | 枚举反馈值；自由文本继续留在其原业务表并按权限处理。 |
| `appointment_requested` | 预约写库成功 | 个案 ID；研究导出默认只给是否发生，不附带授权内容。 |

`page_view`、点击每个按钮等细粒度事件先不采集；没有明确分析问题时，这些事件只会增加噪声与隐私负担。事件写入应尽量和对应业务写入同批完成，或采用可识别失败的异步策略，避免把“点击发送”误记为“消息已送达”。

## 导出与权限

已提供命令行导出 `apps/employee/scripts/export-research.mjs`，需 Cloudflare D1 读取权限，并必须指定组织、起止日期、输出目录和用途。输出 `organizations.csv`、`participants.csv`、`events.csv`、`feedback.csv` 及本地 `export-audit.jsonl`。默认文件不含聊天或广场原文、真实身份、邀请码或凭证。这个本地审计记录依赖操作者妥善保存输出目录；它还不是集中式不可篡改审计。

企业侧仍使用现有 HR 聚合规则：不得返回 `anonymous_user_id`、个案编号或原文，样本量不足时抑制。内部研究权限与企业管理权限必须是不同凭证和不同接口。生产数据库访问权本身也应限于少数开发／研究人员；“知道 D1 数据库 ID”不构成授权。

## 首轮可回答的问题

这些问题可以直接从上述表和事件计算，暂不需要看板：每个组织的邀请进入人数、首次聊天比例、匿名主体的使用天数与回访、聊天后是否打开推荐活动、活动开始与完成的差距、广场阅读与参与情况、错误或响应慢发生在哪些环节。不要把风险级别或对话轮数直接称为疗效指标；疗效需要另外设计可解释的评估方法。

## 效果评估补充

内测报告应分开陈述四类证据：触达与使用、主观帮助、产品质量与安全、长期变化。世界卫生组织的[数字健康干预监测与评估指南](https://www.who.int/publications/i/item/9789241511766)也区分日常实施监测与干预效果评估。使用量、满意度或风险分类都不能单独证明心理健康改善。

| 问题 | 建议指标与分母 | 可作出的结论 |
| --- | --- | --- |
| 是否有人愿意开始用？ | 有效邀请进入人数、首次发消息人数／进入人数；按组织、邀请批次和观察期列出。 | 入口可达性与首次使用。 |
| 是否愿意回来？ | 首次使用后 7／14 天内至少再使用一次的人数／已满足完整观察窗口的首次使用人数。 | 持续使用；不能直接解释为疗效。 |
| 当次体验是否有帮助？ | 对完成聊天或活动者提供可跳过的简短问题，例如“这次交流是否让你感觉被理解？”“此刻是否更知道下一步可以做什么？”；同时报作答人数／被询问人数。 | 回答者的即时主观感受；须同时报告未回答率。 |
| 推荐是否有用？ | 推荐后打开／开始／完成活动人数，各以上一步人数为分母；活动 `helpfulness` 的正、中、负分布及作答率。 | 推荐链路是否产生行动及自报帮助。 |
| 是否造成不良体验？ | 用户主动标记“回复不合适／让我更难受”、人工审核确认的安全问题、危机响应失败、模型错误及超时；报告事件数和处理时长。 | 产品质量和安全，不应只展示正面反馈。 |
| 是否有持续变化？ | 如确有研究目标，再选择经验证、适合目标人群的量表，预先固定基线和随访时间；同时报告完整样本、失访人数及缺失数据处理。 | 只能描述观察到的变化；若要声称变化由产品造成，需要更严谨的对照设计。 |

首轮建议只加极短的可跳过即时反馈，不在每轮聊天后反复弹问卷。现有活动数据已经有 `helpfulness`，回访也有回答字段；`pre_score`、`post_score` 在迁移 `0020_activity_helpfulness.sql` 中被清空，不能把它们当作现成的前后效果证据。风险等级是分流和安全信号，不是心理改善分数。

在首次对外报告前，写一页分析约定：测试起止日期、纳入哪些组织与版本、指标定义和分母、排除演示种子数据的方法、重复身份与跨设备无法识别的限制、缺失反馈与失访如何呈现。产品版本和内容版本应随事件留痕；版本变化后的结果分开看。小样本应报告原始人数及区间，避免只给百分比。匿名个体轨迹只供内部研究，企业与评审材料使用达到披露阈值的汇总。

## 实施顺序与验收

1. 已创建新的统一 CARE 数据库并应用至 0023 迁移，未执行演示 seed。企业与公开组织共用业务表；钉钉实名映射仍隔离在 IDENTITY_DB。
2. 已接入网页邀请、浏览器续签和钉钉映射到统一会话；正式部署与真实邀请链接尚未执行。
3. 已为广场和企业聚合查询加入组织边界及测试；上线前仍需对全部对象接口做一轮浏览器验收。
4. 已写入部分 `product_events`；`experience_feedback` 目前只有表结构，问题展示与回答界面尚未实现，不能据此计算主观帮助率。
5. 已提供受 D1 权限保护的假名数据导出命令；默认不含原文或真实身份。
6. 新研究表已加入 180 天清理流程。参与者测试说明仍需更新，准确披露假名关联、研究用途、留存期限和访问范围。

本文件是目标数据契约。迁移、接口、导出和权限验收完成前，不能对外宣称这些能力已经上线。
